# vn.py 中国期货期权分布式交易平台可行性报告

- **版本：** 1.0
- **调研日期：** 2026-11-08
- **调研对象：** [vn.py / VeighNa](https://github.com/vnpy/vnpy) 开源项目及官方网关、应用
- **目标：** Linux 服务器连接期货柜台并执行交易，Windows 客户端展示行情、配置组合和人工下单；之后通过对话迭代功能，并以受控流程测试、发布和回滚。

## 1. 结论摘要

**总体可行，建议以 vn.py 现有组件为底座做分阶段定制。** vn.py 已有 CTP 国内期货及期权网关、可将行情和交易请求转发给多客户端的 RpcService/RpcGateway，以及面向期权的 OptionMaster。无需从零重写交易核心。推荐先做单 Linux 交易服务进程加 Windows 桌面客户端的 MVP，先接仿真账户，确认柜台、品种、交易权限、断线恢复和风控，再接实盘。

目标与现成能力的对应关系如下：

| 需求 | 可复用能力 | 需要补足 |
| --- | --- | --- |
| 服务端连接柜台并负责交易 | Linux 上运行 `MainEngine`、`CtpGateway`、`RpcService`；官方 CTP 网关列有国内期货和期权 | 无界面服务启动器、配置管理、systemd 服务、柜台接入及账户权限验证 |
| Windows 客户端看行情、人工下单 | VeighNa Trader 加 `RpcGateway`；客户端使用远端服务提供的行情和交易接口 | 组合工作流、界面布局、用户权限、断线和行情过期提示 |
| 交易期权组合及风险管理 | OptionMaster 有波动率曲面、Greeks 等期权功能，另有组合和价差类应用 | 按交易员定义实现组合模板、腿订单、净敞口及下单保护；验证目标期权品种 |
| 服务器或客户端代码迭代 | Git 分支、构建、自动化测试、制品发布和客户端升级可串成流水线 | 本对话环境目前没有任何目标 Linux/Windows 主机连接或部署凭据；需事先配置部署代理和权限 |
| 修改后客户端无感知 | 服务端独立升级且保持客户端协议兼容时，桌面 UI 通常不用更换 | 交易进程重启会断开会话；客户端自身代码和协议变化仍需更新/重启，不能承诺任意改动热更新 |

**主要边界：**“可部署到任何 Linux”应理解为部署到经过版本、原生 API、网络和柜台验证的 Linux 主机。官方当前说明推荐 Ubuntu 22.04 LTS 以上；网络 RPC 官方定位于可信网络环境。不能将原始 RPC 端口直接开放到公网。期货公司的 API 版本、前置地址、IP 白名单、实盘权限及服务条款均是项目以外的先决条件。

## 2. 官方项目现状与依据

本报告以调研日可访问的官方主仓库及官方模块说明为依据。主仓库 README 标注 VeighNa 4.5.0、Python 3.10–3.13，并列出 Windows、Linux、macOS 平台；其环境说明具体列出 Windows 11/Windows Server 2022 和 Ubuntu 22.04 LTS 以上版本。README 推荐的 Studio 安装包版本与主仓库版本标记并不完全一致，因此部署时应锁定并验证一套核心、网关和应用版本，不应只凭安装器名称推断兼容性。

官方 CTP 网关通过 `vnpy_ctp` 封装 CTP API，包说明支持 Python 3.10–3.13 和 Windows/Linux/macOS；从源码构建需要相应 C++ 工具链（Linux GCC、Windows Visual Studio）。框架 README 将 CTP 描述为国内期货、期权网关。此描述表示有相应接入模块，不代表每家期货公司、每个 CTP API 版本、每个期权品种或每个账户都已验证。

官方 `vnpy_rpcservice` 基于 ZeroMQ，定位为可信网络（如本机跨进程或公司内网）中的分布式行情和交易路由；一个服务进程可供多个客户端使用。配套客户端 `RpcGateway` 将远端服务包装成 vn.py 网关接口，适合保持标准 Trader 的客户端形态。官方 WebTrader 则以 REST/WebSocket 提供浏览器访问，是另一个可选的 Web 入口，不是 Windows 原生 Trader 的必需组件。

官方 OptionMaster 面向国内期权交易，描述了期权波动率曲面和 Greeks 风险跟踪等功能。它可以作为期权研究和风险界面的起点，但仍需用目标账户的合约、行情、持仓和交易回报进行实测。项目 README 还列出 SpreadTrading、PortfolioManager 和 RiskManager 等可选应用；是否启用应按需求和兼容性验证逐项确定。

主仓库的 [LICENSE](https://github.com/vnpy/vnpy/blob/master/LICENSE) 标注 MIT，适合作为二次开发底座；正式分发前仍应逐一检查所用网关/应用的许可证，以及期货公司 CTP API 的使用和再分发条款。开源许可证不会替代柜台授权或账户交易权限。

## 3. 推荐的系统架构

```text
期货公司 CTP 行情/交易前置
             │ 受限网络、供应商 API
             ▼
Linux 交易服务器（单一活动交易实例）
  MainEngine + CtpGateway + 风控/期权应用
  RpcService：行情订阅、账户查询、委托/撤单、事件推送
             │ ZeroMQ TCP；只经私网/VPN，防火墙白名单
             ├──────── Windows 交易员客户端 A
             ├──────── Windows 交易员客户端 B
             └──────── 可选监控/Web 层
```

**Linux 交易服务器**负责保存柜台会话、行情和交易连接，接收客户端订单并向柜台发单，维护服务进程、日志、配置和版本。服务端使用无 GUI 启动器创建 `EventEngine` 和 `MainEngine`，注册 CTP 与所需应用，配置 RPC，再由 systemd 负责启动、重启和日志收集。官方简单 RPC 示例展示了独立 RPC server/client 的 TCP 请求与发布订阅模式；将其用于交易时应通过官方 RpcService 适配主引擎，而不是把示例的加法服务器直接用于生产。

**Windows 交易员客户端**运行 VeighNa Trader、RpcGateway 及本地 UI 应用。操作员仍可使用行情查看、合约/账户信息、委托管理和下单窗口等框架功能。客户端不应各自连接柜台，也不应保存所有用户共享的实盘密码。组合定义可以放在服务端作为权威配置，客户端负责编辑和展示；保存组合、生成腿订单、提交订单应拆成可追踪的业务步骤。

**可选 WebTrader**可用于只读监控或浏览器访问。官方模块使用 FastAPI REST 与 WebSocket，并通过 RPC 与交易进程交互。若采用，应另行评估 Web 身份认证、会话安全和每个用户的订单权限；不能因为 Web 层有登录令牌就推断底层 RPC 已获得同等保护。

行情、委托和成交事件推送适合实时更新界面，但客户端重连后必须主动重新查询账户、持仓、活动委托和合约等当前状态，并与随后收到的事件协调；只依赖断线期间的推送会遗漏变化。客户端要清楚显示连接状态、最后行情时间、服务器时间和数据是否陈旧。对活动委托和成交，服务器还应提供幂等/去重策略或请求关联标识，避免超时重试造成重复下单。

## 4. 安装与部署建议

### 4.1 版本和主机基线

1. 先选定 Ubuntu LTS 版本、Python 次版本、vn.py 核心、CTP 网关、RpcService、OptionMaster 和客户端版本，并固定到明确版本号/哈希。团队所有环境使用同一份锁定清单。
2. Linux 首选官方列出的 Ubuntu 22.04 LTS 或更高 LTS；配置独立非 root 运行账户、受控时钟同步、持久化日志、磁盘告警和备份。不要把“Linux 支持”解释成任意发行版、任意 libc、任意 CPU 架构均可直接安装。
3. Windows 使用受支持的 Windows 11 或 Windows Server 2022+；安装与服务端兼容的 Python/VeighNa 环境。若以 Studio/Station 管理桌面应用，遵守官方运行要求；若采用独立安装，按锁定依赖制作可重复安装包。
4. CTP 网关包含原生 API 依赖。优先使用官方发布的兼容 wheel；只有在目标环境没有匹配二进制包时才源码构建，并在和生产相同的系统、Python、架构上验证。

### 4.2 安装顺序

建议将下列步骤固化为自动化配置，而不是每台机器手工点击：

1. 下载官方 vn.py 对应版本源码包或发行包，依据官方 README 在 Windows 执行 `install.bat`，在 Ubuntu 执行 `bash install.sh`；开发环境可使用独立虚拟环境和锁定的 pip 依赖。
2. 安装并验证 `vnpy_ctp`、`vnpy_rpcservice`，再按需安装 OptionMaster、RiskManager、PortfolioManager 等模块。生产禁止浮动依赖版本；构建制品应附依赖清单、源码提交号和校验值。
3. 准备开发、仿真、预生产和生产四类配置。交易账户、密码、授权码和前置地址通过权限受控的秘密存储/部署变量注入，不进 Git、文档、镜像或聊天记录。
4. Linux 服务配置启动命令、重启策略、资源限制、日志轮转和健康检查。Windows 客户端使用相同版本的 RPC 协议与 RpcGateway，并配置服务器私网地址。
5. 仿真环境验证连接登录、合约下载、行情订阅、订单和撤单、成交推送、重连及收盘后重启。只有在账户/权限和风险规则核对完成后才转实盘。

`vnpy_ctp` 官方说明还指出源码安装需 GCC 或 Visual Studio。不要默认在服务进程运行中直接 pip 覆盖包；发布应生成新的不可变虚拟环境或版本目录，验证后切换服务指向。

## 5. 中国期货期权功能的适配范围

### 可直接复用或配置的能力

- CTP Gateway 用于目标经纪商提供的 CTP 行情和交易前置；普通期货和部分期权品种可共用连接，但具体支持依赖券商实际提供的 API 和权限。
- Trader 提供基础市场数据、委托、成交、持仓和人工下单操作框架。
- OptionMaster 提供期权相关分析与风险功能基础；SpreadTrading、组合策略和组合管理应用可作为组合处理的实现参考。
- RiskManager 可用于基础的委托数量、活动委托及撤单等限制。它不能取代交易员和期货公司要求的全部合规/账户风控。

### 需要与交易员共同定义并验收的业务

- 组合模板和腿：组合命名、买卖方向、到期月份、行权价、认购/认沽、手数配比及允许的非对称组合。
- 组合下单：顺序发单或尽可能同步执行、限价规则、腿间价格保护、部分成交处理、改单/撤单、失败补救、组合净持仓与逐腿持仓对账。
- Greeks 与风险：Delta/Gamma/Vega/Theta 显示、风险阈值、行情陈旧时禁用操作、保证金和可用资金核对、超限告警及人工确认点。
- 手工操作：快捷键、默认手数和价格、撤单确认、平仓优先级、今昨仓处理、盘口深度展示和操作审计。
- 账户与品种差异：交易所规则、合约乘数/最小变动价位、行权和到期流程、夜盘时段、异常行情和柜台限频。

组合的“同时下单”不是交易所层面的原子操作。多腿订单可能只有部分成交，因此产品设计必须显式显示腿状态、剩余风险和应急处理方法；不能把组合面板视觉上的一次点击宣传成组合原子成交。

## 6. RPC 安全、可用性和交易风险

这是方案最大的技术风险。官方 RPC README 明确将其定位为可信网络内使用。调研到的 vn.py RPC 实现通过 ZeroMQ `send_pyobj`/`recv_pyobj` 处理请求与响应，并对发布内容使用 Python pickle 序列化。现有实现中未看到可依赖的传输加密和身份认证机制。因此：

- **不得将 RPC 请求/发布端口直接映射到公网。** 端口仅绑定私有网卡/隧道地址，并用主机防火墙限制到受控客户端；跨地点访问先经 VPN 或零信任私网入口。
- 对实盘远程访问，优先在 RPC 外增加经过审计的加密与身份边界，或设计替换为经过身份认证、加密、输入校验和限权的协议层。反向代理如果只包一侧流量、不能正确覆盖 ZeroMQ 发布订阅连接，也不构成完整安全方案。
- 交易请求按用户、账户、合约、最大手数/名义金额、价格偏离、频率和交易时段授权；保留请求、响应、柜台回报及配置变更审计，并实现一键停单/撤单处置。
- 网络断开、行情过期、服务端重启、柜台拒单和部分成交必须有明确定义的 UI 状态与恢复流程。重连时从服务端当前快照重建状态；异常时禁止 UI 继续以“看似连接”的状态发单。
- 首期采用单一活动交易服务实例。普通主备进程若同时连同一账户，可能造成重复委托或状态冲突。高可用应在账户会话隔离、主实例 fencing、订单恢复和柜台限制验证后单独设计。
- 生产部署需限权操作系统用户、秘密管理、补丁和依赖扫描、时间同步、告警、日志保留、备份恢复演练，以及明确的值班和手工应急流程。

`pickle` 不适合处理不可信输入；安全隧道只能减少暴露面，不能代替应用层鉴权、授权、审计和最小权限设计。若要让多名交易员通过客户端操作同一服务，还需为“谁能看、谁能改组合、谁能发单、谁能撤单”建模，而不能把网络连通等同于用户授权。

## 7. 通过对话持续开发和自动发布的可行性

这一目标可以工程化，但必须先搭好部署通道。本次工作区没有目标服务器或 Windows PC 的连接信息，也没有部署代理，因此当前能完成研究、文档、代码修改和本地测试，不能直接连接任何客户主机。后续需准备：

1. Git 远程仓库、部署流水线和自托管 runner/受限部署代理；runner 只获准部署指定项目和服务。
2. Linux 主机的 SSH/配置管理权限、生产秘密注入、systemd 服务名、发布目录和回滚命令；凭据存于秘密管理系统，不粘贴进对话。
3. Windows 客户端制品分发机制，例如代码签名安装包、受控更新服务，或域内软件分发工具。桌面程序涉及二进制扩展时，通常必须重新打包并重启客户端。
4. 仿真/预生产账户、可重复的验收数据、日志和监控只读接口。开发代理不得拥有绕过发布门禁直接下真实订单的能力。

配置完成后，对话驱动的交付流程可以是：

1. 把需求写成可讨论的 Given/When/Then 场景，并先确认组合、风险和异常行为。
2. 在指定 slug/worktree 实现变更；先增加失败的验收/单元测试，再实现代码。覆盖组合订单状态机、序列化兼容、权限、断线恢复等关键逻辑。
3. CI 执行格式、静态检查、单元测试和模拟 RPC/网关集成测试；部署候选版本到仿真环境，记录结果和制品哈希。
4. 通过 CTP 仿真验证登录、订阅、下撤单、回报和重启恢复；健康检查确认 CTP/RPC/行情和账户查询状态后，才进入生产发布步骤。
5. 生产端发布新版本目录并受控重启 systemd。若健康检查失败，自动切回上一个制品并告警。协议需兼容当前 Windows 客户端，才能做到“服务端变化而客户端不升级”。
6. UI 或 RPC 协议改变时生成 Windows 安装包，在测试 PC 验收后通过更新通道升级。客户端需要重启的变更应明确安排，不能保证完全无感。

这套自动化能缩短从对话到可验收版本的周期。它不应被理解为 AI 修改实盘代码后无需验证就立即上线。交易系统还要处理运行中的订单、登录会话和持仓；“热替换 Python 模块”可能使内存状态与柜台状态不一致。允许自动发布的范围、实盘门禁、最大可接受中断和回滚条件都应事先写入部署策略。

## 8. BDD/TDD 验收建议

后续按交易员故事逐项开发，先写行为场景，再写失败测试，最后实现。MVP 的关键场景例如：

```gherkin
Feature: 远端期权交易

  Scenario: 交易员从 Windows 客户端查看服务器行情
    Given Linux 服务已连接仿真 CTP 且 Windows 客户端通过受限网络连接
    When 交易员订阅一个有权限的期权合约
    Then 客户端显示合约报价、更新时间和连接状态

  Scenario: 交易员提交组合订单
    Given 组合腿、账户权限和风险限额均已通过校验
    When 交易员确认组合并提交
    Then 服务端记录唯一请求并返回逐腿委托状态
    And 部分成交、拒单或行情过期会显示风险状态并阻止不安全重试

  Scenario: 服务端重启后恢复交易界面
    Given 客户端曾订阅行情且账户存在活动委托
    When 服务端维护重启并且客户端重新连接
    Then 客户端重新获取账户、持仓和活动委托快照
    And 在行情恢复前显示断开或数据过期状态
```

TDD 应至少覆盖订单参数/权限校验、客户端重复请求、部分成交状态机、价格精度与合约乘数、事件顺序、RPC 版本兼容、断线重连和回滚健康检查。仿真只能验证接口流程，不足以证明实盘滑点、容量、柜台容灾或期权组合执行质量。

## 9. 分阶段落地计划

| 阶段 | 交付 | 退出条件 |
| --- | --- | --- |
| 0. 需求与接入核验 | 券商/API/主机/品种/操作流程清单；交易员行为场景和风险边界 | 券商确认 API、服务器 IP、账户权限和仿真环境可用 |
| 1. 连接验证 | Linux headless CTP 服务、Windows RpcGateway Trader、基本行情和人工单 | 仿真登录、行情、下单/撤单和状态恢复通过；RPC 不暴露公网 |
| 2. 交易员 MVP | 组合配置、腿状态、风险提示、日志审计和断线 UI | 代表性期权组合完成 Given/When/Then 验收，异常可人工处置 |
| 3. 自动交付 | CI 测试、Linux 版本化部署/回滚、Windows 客户端签名制品 | 仿真自动发布和故障回滚演练通过 |
| 4. 受控实盘 | 小规模账户/合约上线、监控和值班流程 | 交易员确认风险限额与操作手册，运行记录满足业务要求 |

每阶段都应该保留版本化配置、测试证据、发布制品和回滚路径。任何影响订单语义、风险控制、数据库结构或 RPC 协议的修改都必须重新评估客户端兼容性。

## 10. 主要风险与缓解措施

| 风险 | 影响 | 建议缓解 |
| --- | --- | --- |
| CTP API/经纪商环境差异 | 安装成功但无法登录、订阅或交易 | 在目标 Linux、目标 API 和仿真账户做先导验证；固定兼容版本并记录柜台配置 |
| RPC 信任模型不足 | 未授权用户可能读取数据或提交交易；pickle 输入有额外安全风险 | 不出公网、私网/VPN、防火墙白名单；补充认证、授权、加密、审计和输入约束 |
| 行情/事件短暂丢失 | 界面显示陈旧持仓或漏掉委托状态 | 重连快照与事件协调，显示时间戳和 stale 状态；每日/异常时对账 |
| 组合多腿非原子执行 | 部分成交导致方向/保证金暴露 | 逐腿状态机、敞口限额、止损/补腿规则、明确人工接管流程 |
| AI 自动发布误伤实盘 | 错误修改造成拒单、重复下单或服务中断 | 测试门禁、仿真先行、受限发布器、健康检查、制品回滚；实盘交易规则变更需指定授权门槛 |
| 服务器维护中断 | 活动交易时客户端失联、撤单受阻 | 避开交易时段、发布前检查活动订单、客户端明确断线状态、准备柜台应急方案 |
| Linux 主机网络/时延不合适 | 连接被拒、行情延时或 API 不稳定 | 使用经纪商允许的网络/固定 IP，实测 RTT、丢包、时钟和线路稳定性；主机选择不只看云厂商 |

## 11. 预期资源和前置条件

- 一台运行受支持 Ubuntu LTS 的 Linux 主机，具备稳定到期货公司前置的专线/白名单网络；是否使用云主机由券商确认。
- 一台或多台 Windows 11/Server 2022 客户端，能够通过私网/VPN 访问服务端。
- 期货公司提供并允许使用的 CTP API 版本、行情/交易前置、账户权限、仿真账户和实盘接入流程。
- 由用户决定的组合模板、下单规则、账户边界、风险限额、操作审计保留期限及故障人工处置方式。
- 私有 Git/代码远程、CI runner、主机发布权限与秘密存储；发布代理最小化授权并可审计。
- 项目维护和交易支持责任人；vn.py 是框架而非经纪商服务，开源代码不提供柜台 SLA、交易结果保证或实时运维支持。

## 12. 推荐决策

建议进入阶段 0/1，先确认你的期货公司 CTP 版本、Linux 主机网络条件、期权品种和第一批组合。若这些条件成立，采用“Linux 单实例交易服务 + Windows Trader/RpcGateway + 私有 VPN/防火墙 + 仿真优先”的方案可满足核心方向，并保留后续通过本对话迭代的空间。暂不建议把当前 RPC 原样开放给异地公网客户端，也不建议在未完成身份授权和恢复验证前将多客户端接入实盘。

本次报告是架构可行性研究，不等于已安装、连接券商、部署客户端或验证真实账户。下一步应在用户提供明确的券商接口资料和目标主机条件后做最小连接 PoC；不需要在此之前改造 vn.py 核心交易代码。
